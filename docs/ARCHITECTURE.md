# Architecture

> Status: living document. It records approved design decisions and is updated as the
> project evolves.

## Goal

`vnce` lets developers build graphics, animations and games that run inside a
terminal. Frames can be produced on the **CPU** or on the **GPU**, then converted into
terminal output (styled characters, high-resolution block/braille glyphs, or terminal
graphics protocols where supported).

## Platforms

The engine is **cross-platform** and targets:

- **Windows**: Windows Terminal and the classic console host (conhost).
- **Linux**: common terminal emulators (Kitty, WezTerm, Alacritty, GNOME Terminal, Konsole, xterm, ...).
- **macOS**: Terminal.app, iTerm2, and the emulators above.

## Design decisions

### Terminal layer

- **Escape sequences are generated by our own code** (`vnce_term::ansi`).
- **`crossterm`** is used only for platform-specific work: raw mode, input events,
  terminal size and enabling VT processing on Windows.
- `crossterm` types are **never exposed** in the public API. The engine defines its own
  `Event`, `KeyCode`, `KeyModifiers`, `MouseEvent` types, so the backend can be replaced later.
- The terminal is always restored (raw mode off, main screen, visible cursor), both on
  `Drop` and from a panic hook.
- **Terminal queries** (`vnce_term::query`): when entering, one write asks for XTVERSION,
  Kitty graphics / keyboard support, cell and window size in pixels, Sixel limits and DA1
  (last; every terminal answers it). Answers are read raw before the event loop starts
  (`rustix` on Unix, `windows-sys` on Windows) and exposed as `Terminal::info()`.

### Graphics protocols

`Frame::draw_image(area, &canvas)` shows an image with the terminal's `GraphicsMode`:

- `Protocol(Kitty | Sixel | Iterm2)`: real pixels. Detection order Kitty → Sixel → iTerm2
  from the query answers; `VNCE_GRAPHICS` overrides. GNU screen uses cells; tmux and
  zellij use Sixel when they report it; Kitty works inside tmux through passthrough with
  Unicode placeholders (`U=1` virtual placements, the image id in the foreground color),
  which tmux moves like text.
- `Cells(PixelMode)`: everywhere else.

The terminal tracks the images on screen: unchanged images are not resent, Kitty images
that are gone are deleted, cells of removed Sixel / iTerm2 images are redrawn and the cells
under unchanged ones are not rewritten (that would erase the image). Sixel / iTerm2 images
never touch the last row, which would scroll the screen.

Speed (a 720p frame on the development machine):

- Kitty images are sent as PNG with the fast `fdeflate` encoder (RGB when opaque): 581 KB
  in 4.5 ms for a gradient instead of 4.8 MB of raw RGBA; zlib without the `png` feature.
- Sixel: a 5-5-5 histogram palette, a lookup table for mapping, bands built in one pass and
  encoded on several threads: 15 ms instead of 271 ms. `sixel::Encoder` keeps the palette
  while the colors stay, so animation does not flicker.
- An image redrawn in the same area is compared with the one on the screen at cell level:
  Sixel (and iTerm2 at exact cell resolution) send patches for the changed rows of cells
  (whole images beyond 70 %); Kitty images at exact cell resolution are split into up to
  8 × 8 tiles and only changed tiles are sent. A sprite moving over a 1600 × 880 picture
  costs about 5 KB per frame.
- Finding out whether an image changed costs at most one pass over its pixels: it is
  compared with the image on the screen (stopping at the first difference), not hashed.
  Copies of changed images go into the memory of images that left the screen (up to two
  are kept), and a Sixel image that already has the pixels of its cells is used as it is.
  A full-screen 2000 × 1180 image costs about 1 ms per frame in `draw_image` instead of
  8 ms (Phase 15).
- In Windows Terminal (which applies the `"2;1` Sixel aspect ratio, checked in its source),
  Sixel images are sent at half height with rows two pixels tall (`VNCE_SIXEL_ASPECT`;
  only with an even cell height). Elsewhere, when writing a frame takes longer than 25 ms
  (the terminal is behind), changed images wait up to 3 frames while text, input and game
  logic keep their pace.

### Rendering model

- **Double buffering**: the previous and current frames are kept as cell buffers; only
  the cells that changed are written to the terminal.
- Each frame is assembled in memory and sent with **a single write**.
- **Synchronized output** (`CSI ? 2026 h/l`) is used where supported, to avoid tearing.
- SGR (style) sequences are emitted only when the style actually changes.
- **Color depth detection** (truecolor / 256 / 16); colors are downsampled to the nearest
  supported color.
- Per-frame cost (Phase 12): cells keep the width of their symbol (computed once when it
  is set), `Buffer::diff_iter` yields the changed cells without allocating, escape
  sequences are assembled from a digit table without the formatting machinery, and a jump
  forward on the same row is sent as `CSI n C`. A full-screen truecolor frame of 200 × 60
  cells is written in about 0.9 ms; `cargo run --release --example perf` measures it.

### Pixel modes

| Mode                   | Pixels per cell | Color                        | Status  |
| ---------------------- | --------------- | ---------------------------- | ------- |
| Half-block `▀`         | 1×2             | Each pixel has its own color | Phase 3 |
| Quadrant               | 2×2             | Two colors per cell          | Phase 3 |
| Sextant (Unicode 13)   | 2×3             | Two colors per cell          | Phase 3 |
| Octant (Unicode 16)    | 2×4             | Two colors per cell          | Phase 3 |
| Braille                | 2×4             | Dot color + background       | Phase 3 |
| ASCII ramp             | 1×2             | Works without color support  | Phase 3 |
| Kitty / Sixel / iTerm2 | Real pixels     | Full color                   | Phase 4 |

For two-color modes the best foreground/background pair is chosen per cell. Uniform cells
are drawn as a space with a background color, so they never depend on the font.

`PixelMode::detect` is compatible with every device: `Ascii` without color support,
`Sextant` only on terminals that draw block glyphs themselves (Kitty, WezTerm, foot,
Ghostty), `HalfBlock` everywhere else. `Octant` and `Braille` are opt-in.
`VNCE_PIXEL_MODE` overrides the choice. `PixelMode::available` lists the modes expected to
display correctly on the current terminal (Octant is never listed automatically: as of 2026
almost no font contains the Unicode 16 octant characters).

The block tables are generated from the Unicode character database by
`tools/gen-block-tables`.

### CPU renderer

Own rasterizer in `vnce_raster::Canvas`: Bresenham and anti-aliased (Wu) lines, rectangles,
circles, triangles with a top-left fill rule and per-vertex gradients, sprite blitting,
`Replace` / `Alpha` / `Add` / `Multiply` blending, clipping and PNG loading.
`Font` draws fixed-width bitmap text through the same clipping and blending: a built-in
5×7 font (printable ASCII and the Turkish letters, designed for the engine), custom fonts
from text art, integer scaling for titles.
Optional parallelism may be added later. (Phase 12: scaling large images runs on several
threads; drawing itself stays on one.)

Horizontal spans (rectangles, circles, outlines) and blits work on row slices: opaque
colors are filled directly, and blending over an opaque pixel divides by a constant.
Triangles find the two ends of each row (every edge function is monotonic along a row, so
the covered pixels form one run) instead of testing every pixel of their bounding box;
the pixels drawn are exactly the same. `Canvas::scaled` applies its weights in two passes
on several threads (`ScaleQuality::Fast`, channels within one of the exact result);
`ScaleQuality::Exact` keeps the direct method, selectable per call
(`Canvas::scaled_with`), per terminal (`Terminal::set_scale_quality`) or with
`VNCE_SCALE_QUALITY`.

### GPU renderer

`wgpu` (Vulkan / DX12 / Metal / OpenGL). Frames are rendered offscreen, read back to the CPU and
converted through the same pixel modes. Enabled with a `gpu` feature flag.

- `Gpu::new` prefers a hardware adapter (high performance by default), then a software
  adapter (WARP on Windows, llvmpipe on Linux), else returns `GpuError::NoAdapter` so the
  program can render on the CPU. `VNCE_GPU_BACKEND` and `VNCE_GPU_POWER` override the choice.
- `RenderTarget`: an `Rgba8UnormSrgb` texture (shaders write linear colors, canvases get
  sRGB). `read_into` copies it into a `Canvas`, either immediately or pipelined over two
  buffers (one frame of latency, the CPU never waits for the GPU).
- `Frame::image_pixel_size(area)` gives the exact pixel size an image is shown at in the
  current graphics mode, and `Frame::image_pixel_aspect()` the shape of those pixels, so
  the GPU renders exactly the pixels that are shown, with the right aspect ratio.
- Helpers: `ShaderQuad` (a full-screen shader from one WGSL `shade` function, validated
  with `naga` for readable errors) and `MeshRenderer` (colored meshes with a depth buffer
  and MSAA, lowered to what the adapter supports, lit by a sun and ambient light and faded
  into distance fog per pixel in world space; vertices without a normal stay unlit), with
  a small `Mat4` type and vector helpers. Users can
  also write their own `wgpu` passes; the `wgpu` crate is re-exported.
- A process has one GPU device (`Gpu::new` returns it once it exists). A native window
  that draws with it marks it, and `RenderTarget::show` then hands the texture to the
  window instead of reading it back.

### Native window

`vnce-window` is a `Backend` and a `Driver`: the `Terminal` gives it each finished frame
through `Backend::present` (no escape sequences), and its driver pumps `winit`'s event
loop from vnce's own game loop, so timing and fixed updates stay as in a terminal.

- Images (`GraphicsMode::Native`, "window") are textures in the window's real pixels,
  uploaded only when they change; `Frame::draw_texture` shows GPU textures directly
  (premultiplied when drawn on a transparent background). Images are drawn first and the
  cells over them: default backgrounds are transparent.
- Cells: one instanced draw from a glyph atlas of the bundled JetBrains Mono (fake bold
  and italic); block elements, quadrants, sextants, octants, braille and box drawing are
  drawn by code (`vnce_raster::block_pattern`), so pixel modes and borders line up.
- `vnce::run` (feature `window`) chooses the window, `--terminal` the terminal.

### Quality

- Unit tests next to the code; randomized robustness tests (`tests/robustness.rs` in each
  crate, own deterministic generator) check invariants on thousands of random inputs: no
  panics, nothing drawn outside its area, encoder output that decodes back to the input,
  frames that reach the emulated screen exactly.
- CI (GitHub Actions): fmt, clippy and tests with warnings as errors on Windows, Linux and
  macOS (GPU tests on software adapters), Rust 1.87, `cargo-deny` and the per-crate
  license files.

### Game core

`vnce_game` holds the parts every 2D game needs, without imposing an architecture (no
ECS):

- `ActionMap<A>`: the game asks about its own actions; keys and mouse buttons are bound to
  them and can be rebound at run time.
- Collision: `Aabb`; `move_and_collide` moves a box through solid tiles axis by axis and
  checks every tile on the way (no tunnelling at any speed); `SpatialGrid` for many
  objects.
- `SpriteSheet` / `Animation` (loop, once, ping-pong, per-frame durations) / `Animator`.
- `TileMap` (layers, loaded from text, solid tiles from the `Tileset`, draws only what is
  visible) and `Camera` (follow with smoothing and dead zone, world bounds, shake,
  interpolation with `ctx.alpha()`, pixel-rounded offsets).
- `SceneStack` runs `Scene`s as a `Game`: push / pop / switch / quit transitions, overlays
  drawn over the scenes below, data shared by all scenes. `Timer` and easing curves.
- `Rng`: a seeded xorshift64* generator (no dependency) for level generation; `below`
  uses a multiply-high instead of a modulo for an even spread.
- `SaveFile`: plain-text `key = value` files in the user's data folder (`data_dir`), typed
  access, key bindings stored by name (`KeyCode` and `Binding` implement `Display` and
  `FromStr`), writes through a temporary file; missing or broken files start empty.

### Audio

`vnce_audio` (feature `audio` of `vnce`, off by default because Linux builds need the ALSA
development files):

- `Mixer`: up to 32 voices with volume, pan, speed (linear interpolation, which also
  converts sample rates), looping, fades, music / effects groups, master volume, mute and
  a soft limiter. It needs no device, so it is tested offline and can render to WAV.
- `Audio` (feature `output`): `cpal` on the default device, any sample format, a small
  buffer where allowed. The game thread sends requests through a channel; the audio
  thread mixes without blocking or allocating and publishes which voices play. No device
  means an error, never a panic.
- `Sound`: own WAV decoder (8 / 16 / 24 / 32-bit integer, float, extensible) and encoder;
  OGG Vorbis with `lewton` (feature `ogg`).
- `Synth`: retro sound effects in code (square, saw, triangle, sine, noise; ADSR, slides,
  pitch jump, vibrato, low-pass) with seeded presets; `Melody` renders tunes from note
  names for seamless music loops.

### Runtime

A game loop with a fixed timestep, frame pacing and input dispatch:

- `Game::update` runs at a fixed rate (1–1000 Hz, default 60); `Game::render` runs at the
  frame limit (`FpsLimit::Fixed(1..=1000)` or `Unlimited`, default 60). Both can be
  changed while the game runs.
- Frames follow the clock, never the input: events are handled while waiting for the next
  frame and cannot trigger extra frames.
- Frame time is clamped to avoid the spiral of death; `render` gets an interpolation
  factor (`alpha`).
- `InputState` tracks held keys. Terminals that report key releases (Windows, or the
  kitty keyboard protocol) give exact releases; elsewhere a timeout is used.
- A `Driver` trait (clock + events) makes runs deterministic in tests (`ScriptedDriver`).
- On Windows a wait for console input ends on the system timer's 15.6 ms steps, which
  made 60 FPS frames alternate between 15.6 and 31 ms. `input::poll` waits coarsely only
  while more than 16 ms remain and sleeps the rest in 1 ms steps (the standard library
  uses a high-resolution timer), checking for events in between.
- The methods of `Context` that request a change (`quit`, `set_paused`, `set_fps_limit`,
  `set_update_rate`, `set_graphics_mode`) take `&self` (the values live in `Cell`s), so
  they can be called while the input from `ctx.input()` is borrowed.

### Widgets

Only what games and graphics applications need: `Text`/`Label` (Unicode, wrapping,
alignment), `Block` (box-drawing borders, title), `Gauge`, `Layout` (rect splitting) and
an `FpsOverlay` for debugging.

- Immediate mode: `Widget::render(area, buffer)` every frame; `List` keeps its selection
  and scroll position in a `ListState` (`StatefulWidget`).
- `Layout`: `Length`, `Percentage`, `Ratio`, `Min`, `Max` and `Fill` constraints with
  spacing and margin; shrinks proportionally (`Min` last) when space is short, shares free
  space by weight, gives rounding leftovers to the largest fractions and never leaves the
  area. `Rect::centered` places popups.
- Text (`Span` / `Line` / `Text`, `Paragraph`): styles are layered patches; word wrapping
  keeps wide characters whole and breaks words longer than a row; cut lines end with `…`;
  control characters are never drawn.
- `Block`: plain, rounded, double, thick or ASCII borders on any sides, titles on the top
  and bottom edges (left, center, right), padding. `Gauge` fills in eighths of a cell,
  `FpsOverlay` adds a sparkline, `Clear` resets an area under popups.
- Every widget that uses box-drawing or block characters has an ASCII option.
- Text drawn over Sixel / iTerm2 images is hidden by them, so popups over such images do
  not show; Kitty and cell modes are fine.
